# 06. 운영 조작과 종료 — 명령의 결과를 확인하기

[전체 목차](README.md) · [상세 설계 원본](../go-room-server-design.md)

## 무엇을 위한 기능인가

**운영자가 참가자·룸·서버에 조치를 요청하고 실제 결과를 확인하는 기능이다.**
예를 들어 방해하는 참가자를 내보내거나, 서버 점검 전에 새 게임을 막을 수 있다.
운영 기능을 포함하는 것은 확정 요구다. 아래는 구현할 조작 계약이며 실행 완료 보고가 아니다.
명령 보관 크기·기간, 로그 rotation(파일을 나누어 관리), 종료 제한 시간의 구체적인 값은 초기 제안이며 실측 후 정한다.

## 세 가지 조작

| 조작 | 뜻 | 일상적인 예시 |
|---|---|---|
| kick | 현재 룸의 특정 참가자를 내보낸다. | “이 룸에 있는 A를 내보내자.” |
| room close | 새 입장을 막고 룸의 참가자·상태를 정리한다. | “문제가 생긴 룸을 닫자.” |
| server drain | 새 게임 수용을 막고 진행 중 게임을 기다린 뒤 종료한다. | “점검 전에 진행 중 게임을 마치게 하자.” |

membership은 세션과 룸의 현재 입장 관계다.
kick은 고정 내부 `room_id`와 membership 식별자를 현재 값과 대조한 뒤 연결 종료·퇴장 정리를 요청한다.
운영 경로의 `{id}`도 내부 ID다. 사용자 입력 `room_number`가 재사용돼도 예전 명령이 새 룸에 적용되지 않게 한다.
예전 화면에서 A를 강퇴했는데 A가 이미 다른 룸으로 이동했다면 그 새 연결 관계를 닫지 않는다.
이미 나간 대상은 `no_op`(변화 없음) 결과나 명확한 실패 사유를 기록한다. 룸 변경은 actor, 즉 상태 변경 전담 작업이 수행한다.

## “접수했습니다”와 “실행했습니다”는 다르다

`202 + command_id`는 접수 번호가 발급됐다는 뜻이며 조작 성공을 뜻하지 않는다.
예를 들어 강퇴 접수 직후에는 대상이 여전히 참가 중일 수 있다. 명령 조회로 실제 결과를 확인한다.

| 상태 | 뜻 |
|---|---|
| `queued` | 실행을 기다림 |
| `running` | 실행 중 |
| `succeeded` | 해당 명령의 완료 조건을 실제로 충족함 |
| `failed` | 실행 실패를 확정했고 이유를 알 수 있음 |
| `unknown` | timeout·재시작 등으로 실행 결과를 확정할 수 없음 |

audit은 누가 어떤 명령을 요청했고 어떻게 끝났는지 남기는 감사 기록이다.
실행 상태와 `audit_failed`는 별도다. 실행이 성공해도 완료 기록 저장은 실패할 수 있다.
예약 이후 명령 수명은 서버가 소유하므로 브라우저 종료나 HTTP 요청 취소가 접수된 명령을 취소하지 않는다.
`unknown`은 실패 확정이 아니다. 명령을 자동으로 다시 실행하지 않는다.

## 접수부터 실행까지의 순서

1. 운영 권한·요청 내용을 검사하고 명령 저장소와 admin lane(운영 명령 대기열)의 자리를 예약한다.
2. 전용 audit writer가 재시작 후에도 남도록 접수 기록을 저장한다(durable 저장). 메모리 buffer에 넣은 것만으로는 완료가 아니다.
3. 예약한 lane에 명령을 넣고 나서 `202 + command_id`를 반환한다.
4. actor가 현재 룸 상태·membership을 다시 검사하고 실제 조작을 적용한다.
5. 실행 결과를 저장하고 완료 audit를 기록한다. 운영자는 명령 조회에서 각각의 결과를 읽는다.

admin lane은 운영 명령 전용의 유한 대기열이다. 꽉 차면 새 조작을 거절한다.
끊어진 참가자를 정리하는 control 큐와 용량을 공유하거나 그 슬롯을 빌리지 않는다.
정리를 먼저 처리하고 운영 처리량을 제한해 게임 tick, 즉 계산 단계가 밀리지 않게 한다.
actor는 디스크 쓰기·네트워크 송신·HTTP 완료를 기다리지 않는다.
durable 접수 뒤에는 예약한 자리를 유지한다. 대기열 등록 전 종료로 결과가 불명확하면 `unknown`으로 남긴다.

## 재시도와 중복 실행의 경계

instance ID는 서버가 기동할 때마다 새로 발급하는 실행 식별자다.
idempotency key는 같은 명령 재시도임을 알려 주는 키이며, TTL은 그 기록의 보관 기간이다.
현재 instance·TTL 안에서 같은 운영자와 같은 key로 동일한 내용을 보내면 같은 command를 반환한다.
같은 key에 다른 내용을 보내면 409를 반환한다. 이전 instance를 지정한 운영 POST는 거절한다.
보관 기간 만료와 재시작을 넘는 영구 중복 방지는 보장하지 않는다.
재시작 후 접수만 남은 audit는 보관 범위 안에서 `unknown` 조회 기록으로 복원하며 실행 큐에 넣지 않는다.

## 인증과 감사 기록

게임 guest·룸 비밀번호와 운영 인증을 분리한다. API 서버는 viewer의 조회 권한과 operator의 조작 권한을 검사한다.
운영 화면·API는 운영 환경에서 HTTPS로 제공한다.
조작은 POST(상태 변경 요청)만 사용한다. cookie 인증이면 CSRF 방어와 요청 사이트(Origin) 검증을 적용하고 SameSite 설정만 믿지 않는다.
CSRF는 다른 사이트가 사용자의 로그인 상태를 이용해 원치 않는 요청을 보내는 공격이다. [OWASP 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

audit에는 운영자·command ID·대상 내부 room_id/membership·명령·접수/완료 시각·실제 결과를 남긴다. 디스크 IO는 actor 밖의 전용 writer가 수행한다.
password·hash·salt·요청 전체 payload를 로그나 audit에 기록하지 않는다. 비밀번호 실패는 오류 코드·횟수 등 비밀정보 없는 항목으로 기록한다.
접수 기록을 저장하지 못하면 조작을 거절하고 실행하지 않는다.
실행 뒤 기록 저장이 실패하면 실제 실행 결과를 유지하고 `audit_failed`를 표시하며 신규 조작 접수를 막는다.
기록 실패를 이유로 이미 실행한 명령을 다시 실행하지 않는다.
초기 제안에서 게임 상태는 메모리라 재시작 시 사라지지만 audit 파일은 재시작 후에도 남는 persistent 저장이다.

## drain은 어떤 순서로 진행되는가

`RUNNING`은 정상 수용, `DRAINING`은 새 게임 차단과 기존 게임 대기, `STOPPING`은 종료 정리 단계다.

1. 새 WebSocket 등록·룸 생성·입장·시작을 차단하고 `/readyz`에 503을 반환한다.
2. 진행 중 match(한 번의 게임)는 유지한다. 0개가 되거나 deadline(대기 한계 시각)에 도달하면 STOPPING으로 전환한다.
3. 기존 WebSocket을 명시적으로 close / cancel(연결 닫기·작업 취소)한다.
4. membership을 정리하고 actor와 연결 읽기·쓰기 작업이 끝나기를 기다린다.
5. 정해진 상한 안에서 audit를 flush(남은 기록 저장)하고 HTTP 서버·프로세스를 종료한다.

admission gate는 “지금 새 참가나 시작을 확정해도 되는가”를 보호하는 짧은 잠금 구간이다.
drain 전환과 create·join·start·WebSocket 등록의 최종 commit(상태 확정)은 같은 gate 안에서 처리한다.
검사 후 잠금을 풀고 입장을 확정하지 않는다. 네트워크·actor 응답·비밀번호 hash·긴 게임 계산 동안 잠금을 잡지 않는다.
private 검증 중 drain으로 예약이 취소되면 늦은 검증 결과로 생성·입장을 확정하지 않는다. 수행 중 hash 연산의 즉시 종료는 보장하지 않는다.
[HTTP Shutdown](https://pkg.go.dev/net/http#Server.Shutdown)은 WebSocket 연결을 닫거나 기다리지 않으므로 3~4단계를 별도로 구현한다.
연결·actor 대기와 audit flush에는 설정한 시간 상한을 적용한다.

drain 명령의 `succeeded`는 **새 게임 차단 전환 완료**다. 프로세스 종료 완료는 별도의 서버 진행 상태다.
종료 후 화면 polling이 끊기는 것은 정상일 수 있으며 이를 명령 실패로 단정하지 않는다.
경로와 결과 필드는 [04. 메시지와 API](04-messages-and-api.md)에서 확인한다.

## 구현 후 확인할 것

- 오래된 강퇴 요청이 다른 룸의 연결을 닫지 않는지 확인한다.
- 재사용 번호의 새 룸에 예전 조작이 적용되지 않으며 로그·audit에 비밀번호·검증값이 없는지 확인한다.
- 접수 기록 실패 시 게임에 변화가 없고, 완료 기록 실패 시 실제 결과가 유지되는지 확인한다.
- 중복 재시도·HTTP 취소·재시작에도 명령이 임의로 두 번 실행되지 않는지 확인한다.
- drain 경합에서 차단 이후 새 입장이 확정되지 않고 기존 게임과 종료 정리가 정해진 순서를 따르는지 확인한다.
