# 03. 실시간 동기화

**클라이언트는 조작 의도를 보내고, 서버는 일정한 간격으로 게임을 계산해 전체 상태를 돌려줍니다.**
각 참가자 화면이 서버의 같은 게임 결과를 따라가도록 하는 것이 이 기능의 목적입니다.

확정 요구사항은 **1~6명의 실시간 이동·협동**입니다.
Go reference 3D 이동과 서버 동기화는 구현했으며 실행 검증은 [서버 가이드](../server-guide.md)를 참조합니다. 30Hz·15Hz는 구현의 기본 시작값이며 성능·실제 도착 지연은 미측정입니다. Godot 표시·보간·예측은 후속 구현입니다.

## 계산·전송·화면 표시는 다름

**tick**은 서버의 계산 한 단계이고, **full snapshot**은 그 시점의 전체 상태 묶음입니다.
Hz는 1초에 몇 번 일어나는지, FPS는 화면이 1초에 몇 번 그려지는지를 뜻합니다.

| 항목 | 초기 제안 | 의미 |
|---|---|---|
| 서버 게임 계산 | 30Hz | 약 33ms마다 이동·충돌·협동 규칙 계산 |
| 전체 상태 전송 | 15Hz | 약 67ms마다 최신 전체 상태를 만들어 전송 경로에 전달 |
| 화면 그리기 | 클라이언트에서 별도로 구현 | 수신한 상태를 바탕으로 화면 표시 |
| 운영 화면 조회 | 2~5초 간격 | 운영 요약을 확인하는 별도 주기 |

**15Hz 전송은 화면이 15FPS라는 뜻이 아닙니다.**
33ms·67ms는 목표 주기의 계산값이며 실제 네트워크 도착 지연이나 처리시간을 보장하지 않습니다.
서버 부하와 게임 계산량, 통신 상태를 측정해 주기를 조정합니다.

## 두 사람이 함께 이동하는 예

민수와 지연이 같은 룸에서 장애물을 피해 이동합니다.
민수는 “오른쪽으로 이동”을 보내고, 지연은 “앞으로 이동”을 보냅니다.
서버는 각 입력을 순서대로 검사하고 고정 tick에서 적용해 실제 위치를 결정합니다. 현재 reference는 free-space 3D 이동이며 장애물·충돌·협동 목표는 게임별 후속 규칙입니다.
다음 전송 주기에 두 사람의 결과를 같은 시점의 전체 상태로 묶어 보냅니다.

```text
이동 의도 → 입력 대기열 → 서버 tick에서 검증·적용
                          ├─ 실제 적용 완료 응답(ACK)
                          └─ 주기별 전체 상태(snapshot)
수신한 상태 → 다른 참가자 보간 / 필요 시 내 예측 보정 → 화면
```

서버가 보낸 결과가 기준입니다. 클라이언트가 보낸 좌표·충돌·승패 결과를 신뢰하지 않습니다.
한 룸의 변경은 room actor, 즉 룸 상태를 순서대로 변경하는 담당자가 처리합니다.

## 입력은 순서대로, 성공 ACK는 실제 적용 후

FIFO는 먼저 들어온 입력을 먼저 처리하는 대기열입니다.
초기 설계는 이동 입력과 일회성 버튼 행동을 **모두 FIFO**로 처리합니다.
각 승인 입력을 Apply하고 해당 tick 계산이 성공한 뒤 성공 ACK, 즉 처리 완료 확인 응답을 보냅니다. ACK는 지속 방향이 해당 tick에 반영됐다는 뜻이며 특정 이동 거리 보장은 아닙니다.
대기열에 들어갔다는 사실이나 입장 예약만으로 성공 ACK를 보내지 않습니다.

게임 시작·종료 때 미적용 입력을 정리합니다. 적용 직전에도 현재 게임인지 다시 확인합니다.
정리한 요청에는 실패 응답을 보내며, 적용하지 않은 입력을 성공으로 답하거나 조용히 버리지 않습니다.
이동 입력 여러 개를 하나로 합치는 최적화는 생략된 요청의 응답 규칙을 정한 뒤 검토합니다.

## 다른 참가자와 내 참가자의 표시

**보간**은 수신한 위치들 사이를 이어서 다른 참가자가 부드럽게 움직이도록 표시하는 방법입니다.
**로컬 예측**은 내 조작을 먼저 화면에 반영하고, 서버 결과를 받으면 보정하는 방법입니다.
보간과 예측은 후속 Godot 구현이며, 이 문서에는 작동하는 표시 코드가 없습니다.

민수가 입력 41·42·43을 예측하고 서버 snapshot이 “입력 42까지 적용한 실제 위치”를 담았다면 다음 순서로 보정합니다.

1. **같은 snapshot** 안의 `game_state`, `server_tick`, 자신의 `last_processed_input_seq`를 함께 읽습니다.
2. snapshot의 서버 상태로 기준을 맞춥니다.
3. 그 상태에 이미 포함된 41·42를 예측 대기 목록에서 제거합니다.
4. 아직 포함되지 않은 43을 다시 적용해 현재 화면을 계산합니다.

개별 입력 42의 ACK가 먼저 와도, 그 ACK만으로 예측 입력을 버리지 않습니다.
보정에 쓰는 서버 상태가 아직 입력 42를 포함하지 않았을 수 있기 때문입니다.
Go의 이동·충돌 계산과 Godot의 예측 규칙이 맞아야 합니다. 물리 계산 차이는 별도로 검증합니다.

## 오래된 입력·상태를 구분하는 번호

| 필드 | 초기 설계 계약 |
|---|---|
| `input_seq` | 세션 수명 동안 증가. 새 match에도 유지하며 중복·역순 입력 검사 |
| `match_id` | 서버가 발급한 게임 한 판의 ID. 이전 판의 입력을 거부 |
| `server_tick` | 해당 match에서 실제 계산한 단계 번호. 새 match마다 시작 |
| `snapshot_seq` | 룸 수명 동안 계속 증가. 새 match에도 초기화하지 않음 |
| `last_processed_input_seq` | 참가자별 실제 적용 완료 번호 map. 자신의 `session_id`로 읽음 |
| `revision` | 룸·게임 상태의 변경 버전. 룸 메타데이터 순서 판단에 사용 |

서버는 snapshot의 상태·tick·참가자별 적용 번호를 **같은 시점**에 캡처합니다.
클라이언트는 오래된 snapshot 번호와 종료된 match의 게임 상태를 반영하지 않습니다.
다만 `room.state`의 퇴장·종료 정보는 revision으로 처리합니다. 게임 snapshot 필터로 버리지 않습니다.

## 입장·시작·종료의 전송 순서

**송신 fence**는 중요한 초기 상태와 게임 전환을 앞질러 최신 snapshot이 나가지 못하게 막는 순서 장치입니다.
create/join 응답은 초기 full 상태를 `payload.snapshot`에 담고 중요 FIFO에 먼저 넣습니다.
룸 metadata에는 내부 `room_id`·사용자 입력 `room_number`·`visibility`를 담으며 password·hash·salt는 넣지 않습니다.
그 응답이 보내지기 전에는 해당 연결의 후속 snapshot을 먼저 보내지 않습니다.
`game.started.payload.snapshot`에도 초기 full 상태를 넣어 새 판의 시작 기준을 전달합니다.

시작·종료 때 이전 최신 snapshot을 폐기하고 중요 이벤트와 `room.state`를 순서대로 전달합니다.
이미 쓰기 중이던 이전 snapshot은 그 중요 이벤트보다 먼저 마칩니다.
입장·시작의 중요한 초기 snapshot은 주기 snapshot의 오래된 상태 필터로 버리지 않습니다.

아직 보내지 않은 full snapshot은 최신 것으로 교체할 수 있어 `snapshot_seq` 중간 누락은 정상입니다.
일회성 `game.event`와 요청 응답은 중요 FIFO로 보존합니다. 최신 snapshot 슬롯이 이를 대신하지 않습니다.

## 현재 reference의 계산과 검증 경계

현재 `move` 방향은 x/y/z 필수 finite numeric scalar `[-1,1]`이며 길이가 1을 넘으면 정규화합니다. 속도는 방향 × 5 world units/s, 입력이 없어도 유지하고 `(0,0,0)`으로 정지합니다. 입장 순서 index i는 `(2*i,0,0)`에 spawn합니다. 한 tick의 FIFO 방향 setter들을 적용한 뒤 `dt=1/TickHz`로 한 번 계산합니다. 입력마다 dt를 적분하지 않습니다. 놓친 ticker 신호를 catch-up하지 않아 부하 중 simulation은 wall time보다 느려질 수 있습니다.

서버 실행과 실제 6 WS checker는 [서버 가이드](../server-guide.md)를 참조합니다. checker는 move seq1 ACK, 양의 Z·불변 X/Y·속도 5, stop seq2 ACK 뒤 위치 유지와 동일 capture key `(match_id,revision,server_tick,snapshot_seq)`의 full 상태를 비교합니다. 서버 TickHz를 추측하지 않습니다. 정상 종료는 handler EndReason 경로이고 reference 자동 종료 조건은 없습니다. test handler로 종료·다음 match를 검사합니다. deterministic barrier는 전송 순서와 bounded queue 경합 시험이며 TCP 손실·jitter 주입 시험은 아닙니다. Godot QA와 부하·화면 지연은 미측정입니다.

## WebSocket의 한계와 후속 확인

WebSocket이 사용하는 TCP에서 데이터가 손실되면 뒤 데이터도 순서를 기다릴 수 있습니다.
최신 snapshot 교체는 이미 전송 중인 TCP 데이터의 지연까지 없애지 못합니다.
요구가 빠른 경쟁 게임으로 바뀌면 UDP 계열을 검토합니다.

- 실제 6클라이언트로 같은 match의 같은 revision·tick에서 공개 상태가 일치하는지 확인합니다.
- 지연·흔들리는 지연·손실·느린 수신자 조건에서 입력 순서와 성공 ACK의 적용 시점을 확인합니다.
- 보정에 사용한 상태·tick·입력 번호가 같은 snapshot에 속하는지 확인합니다.
- 시작·종료 순서 장치와 일회성 이벤트 보존, 실제 tick·전송 주기·화면 지연을 측정합니다.
