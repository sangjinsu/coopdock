# 02. 룸과 세션

**친구가 알려 준 룸 번호로 들어가고, 프라이빗 룸이면 생성자가 정한 비밀번호를 입력합니다.**
한 연결은 한 룸에만 속하며 대기 중인 룸만 새 참가자를 받습니다.

확정 요구사항은 **룸당 1~6명, 번호로 입장, 프라이빗 비밀번호 확인**입니다.
번호 6자리·기본 공개·비밀번호 길이 등 세부값과 아래 상태·퇴장 규칙은 **초기 설계 제안**입니다.
이 문서는 목표 설계입니다. 현재 연결·룸 관리 구현과 검증 범위는 [서버 가이드](../server-guide.md)를 참조하세요.

## 먼저 알아둘 신분

| 단어 | 뜻 |
|---|---|
| guest 세션 | 연결 하나에 서버가 발급한 `session_id`. 운영 계정과는 별개 |
| 룸 | 참가자가 모여 기다리거나 게임을 하는 방 |
| `game_id` | 연결 때 선택해 고정되는 공개 게임 namespace. 인증 정보가 아님 |
| `room_number` | 게임 안에서 고유한 번호 문자열. 예: `"004271"` |
| `room_id` | 서버가 발급하는 고정 내부 ID. 운영 조작·입장 관계의 기준 |
| `visibility` | 공개 `public` / 프라이빗 `private` 구분 |
| membership | “이 세션이 지금 이 룸에 속한다”는 현재 입장 관계 |
| host | 방장. 게임 시작을 요청할 권한을 가진 참가자 |
| match | 그 룸에서 진행하는 게임 한 판. 새 판에는 새 `match_id` 사용 |

게임 등록은 `GAME_IDS`, URL 선택·version 1의 guest/full snapshot `game_id` 추가와 strict client 동시 업데이트는 [현재 서버 계약](../server-guide.md)을 따릅니다. 전역 자원 한도와 공통 이동 handler는 게임들이 공유합니다.

초기 guest 연결은 이전 연결의 상태를 복원하는 로그인 기능이 아닙니다.
연결이 끊겨 새로 접속하면 서버는 새 guest 세션으로 처리합니다.

## 번호로 입장하는 흐름

초기 번호는 **ASCII 숫자 6자리 문자열**로 제안합니다. 앞에 0이 있는 `004271`도 그대로 입력합니다.
활성 룸의 번호는 같은 게임 안에서 겹치지 않고 해당 룸이 닫힐 때까지 유지됩니다. 서로 다른 게임은 같은 번호를 가질 수 있습니다.
create/list/join은 연결에 고정된 게임만 대상으로 하며 다른 게임에만 있는 번호는 `ROOM_NOT_FOUND`입니다. 게임을 바꾸려면 연결을 끊고 새 guest를 발급받습니다.
닫힌 번호는 나중에 새 룸이 사용할 수 있으며 서버 재시작 시 번호도 사라집니다.
번호는 룸을 찾는 주소이며 비밀번호를 대신하지 않습니다.

```text
룸 번호 입력 → room.join 요청
                 ├─ 공개 룸 → 상태·정원 확인 → 입장
                 └─ 프라이빗 → PASSWORD_REQUIRED → 비밀번호 입력
                                  → 같은 번호 + 비밀번호 재요청
                                  → 검증·상태·정원 확인 → 입장
```

없는 번호는 `ROOM_NOT_FOUND`, 숫자 6자리 형식이 아니면 `INVALID_MESSAGE`입니다.
프라이빗의 비밀번호가 맞지 않으면 `PASSWORD_INVALID`를 받습니다.
반복 시도 제한은 `RATE_LIMITED`, 서버의 비밀번호 처리 대기열 포화는 `SERVER_BUSY`입니다.
별도의 “번호 조회” 메시지는 만들지 않고 `room.join`의 응답으로 필요한 입력을 안내합니다.

| 공개 여부 | 생성할 때 | 참가자가 입장할 때 | 플레이어 룸 목록 |
|---|---|---|---|
| `public` | 비밀번호 없음. password 필드를 보내면 오류 | 번호만 입력 | 표시 |
| `private` | 생성자가 비밀번호 지정 | 번호와 비밀번호 입력 | 제외 제안 |

공개 여부의 기본값은 `public`, 비밀번호는 **4~64 Unicode 문자(code point)**를 제안합니다.
대소문자를 구분하며 서버는 앞뒤 공백을 임의로 제거하거나 Unicode 정규화를 하지 않습니다.
private 생성에서 비밀번호 누락·잘못된 길이는 `INVALID_MESSAGE`입니다.
룸이 살아 있는 동안 공개 여부와 비밀번호를 고정합니다. host가 바뀌어도 생성자가 지정한 비밀번호를 유지합니다.
비밀번호 변경·초기화 기능은 이번 설계에 추가하지 않습니다.

## 세 사람이 프라이빗 방을 만들고 시작하는 예

1. 민수가 정원 3명·private·비밀번호를 지정해 만듭니다. 민수는 자동 입장하고 방장이 되며 번호 `004271`을 받습니다.
2. 지연과 도윤은 그 번호와 비밀번호로 입장합니다. 서버는 입장 순서를 민수 → 지연 → 도윤으로 기억합니다.
3. 지연이 시작을 요청하면 `NOT_HOST`입니다. 민수가 요청하면 게임을 시작합니다.
4. 게임 중 도윤이 나가면 서버는 퇴장을 반영하고 게임 규칙에 알립니다.
5. 게임이 끝나면 같은 참가자들이 다시 대기 상태로 돌아갑니다. 계속 참가 중이므로 비밀번호를 다시 입력하지 않습니다.

참가자가 줄었다고 반드시 게임을 끝내지는 않습니다.
계속 진행할지, 인원 부족으로 종료할지는 게임 규칙인 `GameHandler`가 결정합니다.

## 룸 상태와 기본 규칙

```text
생성 + 생성자 입장 → WAITING → 방장의 시작 → PLAYING
                        ↑                     │
                        └── 게임 종료·초기화 ──┘
마지막 참가자 퇴장 또는 운영 close → CLOSED → 룸 목록에서 제거
```

| 항목 | 초기 설계 제안 |
|---|---|
| 정원 | 지정하지 않으면 6명. 지정할 때는 확정 범위인 1~6명 검증 |
| 생성 | 생성자가 자동 입장. 확정 실패 시 미게시 룸·번호·세션 예약을 정리 |
| `WAITING` | 대기 상태. 공개는 번호, 프라이빗은 번호·비밀번호 확인 후 입장 허용 |
| `PLAYING` | 게임 진행 상태. 올바른 비밀번호가 있어도 새 입장·재입장을 거부 |
| `CLOSED` | 닫힌 상태. 대기 요청에 `ROOM_CLOSED`를 반환하고 목록에서 제거 |
| 시작 | 현재 host만 요청 가능. 혼자 있어도 시작 가능 |
| 한 세션의 소속 | 입장 확정과 정리가 끝나는 동안 다른 룸으로 동시에 들어갈 수 없음 |
| host 퇴장 | 남은 참가자 중 가장 먼저 입장한 사람이 승계. 공개 여부·비밀번호 유지 |
| 마지막 참가자 퇴장 | 즉시 룸을 닫고 목록에서 삭제 |
| 게임 종료 | 게임 상태를 초기화하고 `WAITING`으로 복귀 |

룸 목록을 보거나 비밀번호가 맞는지 확인한 직후 다른 사람이 마지막 자리를 차지할 수 있습니다.
따라서 실제 입장 시점에 서버가 정원과 상태를 다시 확인합니다.

## 마지막 자리에 두 사람이 동시에 들어오면

정원 3명의 방에 민수와 지연이 있고, 도윤과 하늘이 동시에 입장한다고 가정합니다.
룸 담당자가 **자리 확인과 참가자 추가를 하나의 작업**으로 처리해 한 사람만 입장시킵니다.
뒤에 처리된 요청은 `ROOM_FULL`을 받습니다. “목록에서 빈자리였음”은 입장 보장이 아닙니다.

입장 요청 중에는 세션에 `JOINING` 예약을 두고, 확정하면 `JOINED`가 됩니다.
이 예약은 **같은 세션의 중복 입장을 막는 장치이며 빈자리를 확보한 상태가 아닙니다.**
**generation**은 이 예약이 몇 번째인지 구분하는 내부 번호입니다.
요청 시간이 끝났거나 연결이 끊기면 예약을 무효화해 뒤늦게 도착한 입장을 막습니다.

private 비밀번호 검증은 룸 actor 밖의 제한된 worker가 담당합니다.
검증이 끝난 뒤 actor는 같은 세션 잠금 안에서 generation·연결·현재 소속을 재확인합니다.
대상 룸의 `WAITING`·정원과 서버 수용 gate도 다시 확인하고 참가자 추가와 소속 확정을 함께 처리합니다.
이미 입장이 확정됐으면 퇴장 정리 경로로 제거한 뒤 예약을 해제합니다.
그 정리가 끝나기 전에는 다른 룸 입장을 허용하지 않습니다.
늦은 결과의 generation이 예전 번호이면 새 예약이나 현재 룸을 변경하지 않습니다.

번호를 처음 조회했을 때의 실제 `room_id`도 검증 결과에 묶습니다.
늦은 결과를 `room_number`로 다시 조회하면 같은 번호를 재사용한 새 룸으로 들어가는 문제가 생길 수 있습니다.
따라서 서버 내부의 `room_id`·generation을 대조하며 클라이언트가 주장하는 “비밀번호 검증 성공”은 신뢰하지 않습니다.
검증 중 disconnect·timeout·drain·room close가 발생하면 예약을 취소하고 늦은 결과를 거절합니다.

## 비밀번호 작업이 플레이를 멈추지 않도록

원문은 저장하지 않고 룸마다 다른 무작위 salt와 Argon2id 검증값(hash·계산 설정)을 서버 내부에 보관합니다.
salt는 같은 비밀번호라도 다른 검증값을 만들도록 더하는 무작위 값입니다. [OWASP 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
비밀번호 계산은 actor 밖에서 실행하며 동시에 실행할 worker 수와 대기량에 상한을 둡니다.
private 생성도 이 계산 뒤 생성 조건을 다시 확인하고 실패한 룸·번호·예약을 정리합니다.
[Go argon2.IDKey](https://pkg.go.dev/golang.org/x/crypto/argon2#IDKey)는 context를 받지 않아 요청을 취소해도 이미 수행 중인 계산이 즉시 끝난다고 보장할 수 없습니다.
actor 밖의 작업도 CPU·메모리를 쓰므로 반복 입장 시 게임 tick 영향을 실제로 측정해야 합니다.

실패 시도는 IP·세션·룸별로 일정 시간(TTL) 제한하는 방식을 제안합니다. IP는 신뢰할 proxy 정책으로 판단합니다.
전체 worker 상한도 적용하며 다른 참가자까지 영구 차단하는 전체 룸 잠금은 두지 않습니다.
횟수·TTL·worker 수는 미측정 설정입니다. [참고한 throttling 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling)
게임 통신은 운영 환경에서 WSS를 사용하며, 응답·snapshot·운영 화면·로그에 password·hash·salt를 포함하지 않습니다.

## 게임 중 연결이 끊겼다가 돌아오면

민수·지연·도윤이 `PLAYING` 상태에서 협동 중이고, 지연의 연결이 끊겼다고 가정합니다.

1. 서버는 지연의 현재 membership을 정리하고 게임 규칙에 퇴장을 알립니다.
2. 민수와 도윤의 게임은 기본적으로 유지됩니다. 인원 부족 처리는 게임 규칙에 따릅니다.
3. 지연이 다시 연결하면 **새 guest 세션**입니다. 이전 플레이어 상태를 자동 복원하지 않습니다.
4. 이전 룸이 아직 `PLAYING`이면 입장 요청은 `ROOM_IN_PROGRESS`로 거부됩니다.
5. 그 룸이 살아 있고 게임 종료 후 `WAITING`으로 돌아오면, 지연은 번호로 새 입장을 요청할 수 있습니다. private면 비밀번호를 다시 확인합니다.

퇴장 후 같은 연결로 다시 입장해도 새 membership이므로 비밀번호를 확인합니다.
생성자 자동 입장이나 membership 유지 중 게임 시작·다음 판에는 별도 재입력이 없습니다.

**자동 재접속 복원은 초기 범위 밖**입니다. 서버 재시작 때도 세션·룸·게임 상태가 사라집니다.
퇴장 처리 중 게임 규칙의 후속 알림이 실패해도 끊어진 세션을 참가자로 되돌리지 않습니다.

## 운영 kick은 현재 입장 관계를 확인

kick은 운영자가 참가자의 현재 입장을 종료하는 명령입니다.
지연이 룸 A를 떠나 룸 B로 옮겼는데, 늦은 룸 A의 kick이 도착할 수 있습니다.
서버는 **내부 `room_id`와 membership 식별자**를 현재 값과 대조합니다. 사용자 입력 번호를 운영 명령 대상으로 대신하지 않습니다.
전역 session ID만 보고 룸 B에 있는 연결을 닫지 않습니다.
실제 조작 결과는 [운영 조작 문서](06-operations-and-shutdown.md)에서 확인합니다.

## 구현 후 확인할 기준

- 공개 번호 입장과 private 비밀번호 요청·검증·재요청이 정해진 순서를 따르는가?
- `004271`의 앞 0을 보존하고 활성 번호가 중복되지 않으며 host 승계에도 비밀번호가 유지되는가?
- 동시에 입장해도 정원을 넘지 않고, 같은 세션이 두 룸에 남지 않는가?
- 입장 timeout·disconnect와 늦은 결과가 겹쳐도 예전 membership이 남지 않는가?
- 번호가 재사용되거나 검증 중 룸이 닫혀도 늦은 결과가 새 룸으로 입장시키지 않는가?
- 비밀번호 처리 포화·반복 요청을 제한하면서 게임 tick 영향을 측정하고 비밀정보 노출이 없는가?
- host 승계가 입장 순서를 따르고, 빈 룸과 실패한 생성 룸이 목록에서 제거되는가?
- `PLAYING` 재입장을 거부하며 게임 종료 후 입장은 새 참가자로 처리하는가?
- 예전 룸의 kick이 다른 룸으로 옮긴 세션을 닫지 않는가?
